# Git 不只是 commit：分支策略与可读的提交历史

刚接触 Git 时，我对它的全部理解是：`git add`、`git commit`、`git push`，三连完成就算会用。直到在一次小组项目里，四个人往同一个分支上推代码，提交记录长这样："修改"、"fix"、"又改了一下"、"最终版（真的）"，回滚历史时我们花了整整一个晚上。

![夜空下的分支树配图 w-100](/assets/posts/git-workflow.webp "提交历史是一棵树")

从那以后我开始认真对待 Git 的工作流，这篇文章是一些沉淀。

## 提交信息是写给未来读者的

提交信息的读者不是现在的自己，而是三个月后想回滚某个功能、或者排查"这行代码为什么被改"的人。我现在遵循的格式很简单：

```
feat(order): 支持订单列表按状态筛选
fix(auth): 修复 token 过期后未跳转登录页的问题
docs: 补充接口文档的幂等性说明
```

要点有两个：类型前缀让历史可以被快速扫描；描述写"做了什么"而不是"改了哪个文件"，文件列表 Git 自己记得。

## 分支的意义：让不稳定的变化彼此隔离

单人项目里，分支策略可以很简单；多人项目里，它的价值就显现出来了。我现在常用的结构是：

- `main`：永远可部署，只在发布或合并时更新；
- `dev`：集成分支，功能先在这里汇合验证；
- `feature/xxx`：每个独立功能一条分支，做完就合并删除。

这带来的不只是整洁，更是一种保险：一个功能写坏了，最坏情况是扔掉那条分支，主线的稳定性不受影响。**隔离不稳定的变化**，是分支存在的根本理由。

## merge 还是 rebase：先想清楚历史的用途

这两个命令我纠结了很久，后来想明白它们的区别在于"你想让历史讲述什么故事"：

- `merge` 保留真实的分支拓扑，忠实记录"什么时候、由谁、合并了什么"，适合公共分支之间的合并；
- `rebase` 把提交挪到新的基点上，历史变成一条直线，适合在推送前整理自己本地的提交。

我给自己定的规则是：**公共分支用 merge，私有分支随便 rebase**。切记不要 rebase 已经推送到远端且他人基于它开发的分支，那等于改写了别人的历史。

## 几个救过我的命令

- `git reflog`：所有 HEAD 的移动记录，reset 错了也能从这里找回提交；
- `git revert`：生成一个反向提交来撤销变更，比直接改历史安全，适合公共分支；
- `git stash`：临时收起半成品，切去处理紧急问题后 pop 回来；
- `git blame -w`：忽略空白差异地查看每行最后修改者，排查时少很多噪音。

工具的意义在于犯错之后还有回头路，这几个命令就是回头路本身。

## 小结

Git 工作流不是炫技的仪式，而是团队协作成本的直接体现。提交信息清晰、分支职责明确、历史可回溯，这三件事做到之后，代码评审和问题排查都会顺畅很多。

对我来说，Git 从"上传代码的工具"变成了"团队沟通的媒介"——每一次提交，都是写给协作者的一条留言。
