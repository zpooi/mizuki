# 从 Linux.do 学来的解决办法：把问题变成可复用的方案

上次整理了[几篇 AI 主题的好帖](/posts/linuxdo-ai-posts/)，这篇换个角度：记录那些**带着完整解决过程**的帖子。对我而言，一个解决办法的价值不在结论本身，而在于作者如何定义问题、如何取舍、如何验证——这些才是可以迁移的能力。

![解决办法配图 w-100](/assets/posts/linuxdo-solutions.webp "把问题一个个解决掉")

## 一、零成本聚合大模型 API：自己搭一个网关

很多同学都在用各家大模型，但每家的 SDK、额度、计费方式都不一样，切换模型就要改一遍代码。社区里常见的解决办法是：**申请几家的免费额度，然后用 new-api / one-api 这类开源网关统一成 OpenAI 兼容接口**。

思路大致是：

1. 收集免费渠道，比如智谱的 GLM-Flash 系列、硅基流动的新人额度、火山引擎豆包的每日免费 Token 等（各家政策随时会变，以官方页面为准）；
2. 用 Docker 一行命令部署 new-api（`calciumion/new-api:latest`），挂载好 `/data` 数据卷；
3. 在网关后台把各家的 Base URL 和 Key 配置成"渠道"，设置重试和分组；
4. 应用侧只对接网关这一个地址，换模型只是改一个模型名。

这个方案真正教会我的是**抽象层的价值**：在应用和供应商之间加一层稳定的接口，变化就被隔离在网关里了。这和后端开发里"防腐层"的设计思想是同一件事。

## 二、免费算力训练模型：从 API 到微调的完整链路

另一篇让我印象很深的帖子把"零成本玩模型"串成了完整流水线：免费申请 API Key（如 Akash 提供的 LLaMA 系模型）→ 用 easy-dataset 自动化构建问答数据集 → 用 LLaMA-Factory 做 LoRA / QLoRA 微调 → 全程用 Docker 容器化部署中间件。

作者把每个环节的工具、配置和坑都列了出来，包括用容器方式部署 clash 解决网络连通性这类细节。虽然单个环节不复杂，但**把推理、数据、微调串成一条可复现的链路**，正是很多教程缺失的部分。

我的笔记是：微调前先想清楚是不是真的需要微调——多数场景下，把上下文写好、配合检索（RAG）的收益比直接微调更大，成本也低一个量级。

## 三、Cloudflare Worker 实战：把一次性脚本变成长期服务

有一位佬友的经历特别典型：换了新代理内核后，很多客户端不支持扩展脚本，与其到处找支持的客户端，不如**在服务端用 Cloudflare Worker 写一个订阅转换服务**。

这个帖子的可学之处在于演进过程：

- 先在阿里云云函数上试，发现取上游资源和 GitHub 上的 geo 数据很费劲，果断换到 Cloudflare Worker；
- 用 hono 框架 + wrangler 工具链，调试和部署体验都很好；
- 功能上做了地区分组、防 DNS 泄露、Token 管理订阅、按地区/倍率/正则过滤节点，还处理了 iOS 端不支持 `geosite:private` 的兼容问题。

"先试一条路，遇到摩擦就换更顺手的工具"——这个决策过程比最终代码更值得学。

## 四、遇到问题，先看看别人怎么解决的

社区里还有大量更小的"解决办法"：在免费 PaaS 上部署哪吒面板的步骤化记录、管理 Docker 容器流量的讨论、知识库大文件的同步思路……单个看都不惊天动地，但它们共享同一个模式：

**把一次性的排查过程，显性地写成可复现的步骤。**

这正是我一直想在自己博客上坚持的事情。很多问题的答案搜索引擎里其实有，但"完整的上下文 + 为什么这样做 + 踩过什么坑"只有认真的记录者才会写出来。

## 小结

解决办法帖读多了会发现，高手解决问题的方式出奇一致：先定义问题（我要什么、约束是什么），再拆解环节（每一步用什么工具、怎么验证），最后把整个过程沉淀成可复现的文档。

技术会过时，工具会更替，但这个模式不会。感谢 Linux.do 上认真写帖的佬友们，也希望我的记录有一天能帮到别人。
