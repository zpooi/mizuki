# 接口设计中的边界感：统一响应、错误码与版本管理

前后端联调时，大多数争吵的根源不是技术，而是"我们当时没说清楚"。字段为空返回 `null` 还是 `""`？错误是返回 200 加错误码，还是直接返回 4xx？这类问题如果没有提前约定，联调阶段就会反复返工。

![接口如桥配图 w-100](/assets/posts/api-design.webp "接口是两端之间的桥")

这篇文章整理我在接口设计上的一些原则和思考，很多来自联调时真实的教训。

## 统一响应结构：先定骨架，再填内容

我们项目最终采用的响应结构很简单：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

看似平淡，但它带来两个好处：前端可以写一套统一的拦截器处理成功与失败，不用每个接口单独判断；后端通过全局异常处理器兜底，业务代码里不需要到处写 try-catch 拼装响应。

我的体会是，响应结构本身不重要，**全项目只有一种结构**才重要。一旦出现"某些接口直接返回数据、某些接口包了一层"，前端的处理逻辑就会开始分叉。

## 错误码要成体系，而不是随手编

错误码设计的常见误区是拿 HTTP 状态码当业务错误码用，或者干脆每个错误一个随机数字。我的做法是把错误码分段：

- `0` 表示成功；
- `4xxx` 段表示客户端问题，如参数错误、未登录、无权限；
- `5xxx` 段表示服务端问题，如数据库异常、依赖服务不可用；
- 每个错误码在代码里都有唯一的枚举定义和默认提示文案。

这样排查问题时，看到错误码就知道问题出在哪一侧，不需要复现路径。配套的一点是：**给用户的提示和给开发的日志要分开**。"系统繁忙"是给用户的，具体堆栈在日志里。

## 校验前置：让非法请求死在门口

参数校验的位置会显著影响代码整洁度。最好的位置是入口：用注解校验（如 `@Valid` + `@NotNull`）在 Controller 层直接拒绝非法请求，而不是让它们穿透到 Service 甚至数据库层再报错。

校验前置还有一个隐性收益：它强迫设计接口时想清楚"合法的输入长什么样"。如果一个字段允许的范围连自己都说不清楚，那这个接口的边界就是模糊的。

## 版本管理：为变化留后路

接口一旦发布，就有别人在依赖它。App 端的接口尤其如此：用户不一定会更新版本，老版本客户端可能要运行很久。

实践中比较务实的做法：

- 在 URL 中带版本号（`/api/v1/...`），出现不兼容变更时新增 `v2`，而不是原地修改；
- 字段只增不改：新增字段是兼容的，修改字段含义、改变字段类型几乎必然出事；
- 下线接口提前公告，并观察旧版本的调用监控，确认没有流量再移除。

## 幂等：被低估的设计约束

涉及支付、提交订单这类写操作时，幂等性值得提前考虑。网络重试是常态，同一个请求可能到达两次。简单可靠的做法是让客户端带上幂等键，服务端据此判断是否重复处理。这个约束放在设计阶段考虑成本很低，事后补就麻烦得多。

## 小结

接口设计的核心是管理预期：响应结构约定了成功时的样子，错误码约定了失败时的样子，校验约定了输入的边界，版本管理约定了未来变化的规则。

好的接口文档只是结果，真正的功夫在设计阶段就把边界谈清楚。这大概就是"边界感"在工程里的含义。
