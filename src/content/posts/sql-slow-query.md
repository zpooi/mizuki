# 从一条慢查询开始：索引、执行计划与 SQL 调优入门

在政务大屏项目里，我遇到过这样一条查询：本地测试环境数据量小的时候毫秒级返回，部署到演示环境之后，页面刷新时明显卡顿。打开监控一看，罪魁祸首是一条看起来很普通的列表查询。

![深夜调优 SQL 配图 w-100](/assets/posts/sql-tuning.webp "深夜与慢查询")

这篇文章记录我当时排查和优化的完整思路，作为自己数据库学习的一个阶段性笔记。

## 第一步：确认问题真的在数据库

遇到"页面慢"，第一反应不应该是直接改 SQL。页面加载慢可能出在网络、序列化、前端渲染等很多环节。我当时的做法是：

1. 在后端日志里记录接口耗时，确认慢发生在哪一层；
2. 如果确认是数据库层，再记录具体的 SQL 和参数；
3. 拿到 SQL 之后，先看它扫描了多少行、返回了多少行。

扫描行数远大于返回行数，通常就是优化空间最大的地方。

## 用 EXPLAIN 代替猜测

MySQL 的 `EXPLAIN` 是调优时最基础也最有用的工具。看执行计划时，我最关注几个字段：

```sql
EXPLAIN SELECT o.order_no, u.username
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1
  AND o.created_at >= '2026-09-01'
ORDER BY o.created_at DESC
LIMIT 20;
```

- `type`：如果是 `ALL`（全表扫描），基本可以确定缺少合适的索引；
- `rows`：预估扫描行数，和返回行数差距越大，说明做了越多无用功；
- `Extra`：出现 `Using filesort` 或 `Using temporary` 时，排序和分组往往没有走索引。

一开始我习惯背"什么情况走索引、什么情况不走"，后来发现真正有效的学习方式是：写一条查询，跑一次 EXPLAIN，观察结果，改一下再观察。执行计划给出的答案永远比口诀可靠。

## 索引不是越多越好

确认缺索引之后，下一个问题是建什么索引。我踩过的坑是"哪里查询慢就在哪个字段上加索引"，结果表上挂了一堆单列索引，查询依然慢，写入反而变慢了。

后来我理解了几条更实用的原则：

- **联合索引优于多个单列索引**。把 `status`、`created_at` 这类高频组合条件按顺序放进一个联合索引，往往比两个孤立的单列索引有效得多；
- **最左前缀原则**决定联合索引能不能被用上，列的顺序要按查询习惯设计；
- **索引也要有成本**。每次写入都要维护索引，更新频繁的表更需要克制。

优化完成的标准不是"加了索引"，而是再跑一次 EXPLAIN，确认扫描行数确实降下来了。

## 写法习惯同样重要

有些慢查询和索引无关，纯粹是写法问题。我整理了几条自己常犯的错误：

- 在 `WHERE` 条件里对索引列使用函数或运算，会让索引失效；
- `SELECT *` 会让覆盖索引失效，按需取列是低成本的好习惯；
- 深分页 `LIMIT 100000, 20` 会扫描并丢弃前十万行，可以改用游标式分页（记录上一页最后一条的位置）；
- 大批量更新拆成小批量执行，避免长事务锁住大量行。

这些习惯单看都不复杂，难的是在写代码的时候一直记得它们。

## 小结

这次调优让我对"数据库优化"有了更具体的理解：它不是背一堆规则，而是一个"观察执行计划 → 提出假设 → 验证结果"的循环。索引是手段而不是目的，优化的终点永远是那条真实的业务查询。

以后遇到新的慢查询，我的第一反应会从"加个索引试试"变成"先看看 EXPLAIN 怎么说"。
